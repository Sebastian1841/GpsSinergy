# Views

Pantallas principales conectadas al router.

## Archivos

- `a.html`: documentacion HTML auxiliar usada aparte por el usuario. Debe mantenerse sincronizada con los cambios grandes de arquitectura, flujos, reportes y organizacion del frontend. No eliminar sin confirmacion explicita.
- `b.html`: documentacion HTML auxiliar sobre mejora del sistema de mantenciones. No esta conectada al router y debe tratarse como informe de referencia, no como vista Vue.
- `ActivosView.vue`: vista principal de monitoreo de activos. Tambien acepta `?activoId=`, `?assetId=` o `?asset=` para seleccionar un activo desde navegacion externa, como el buscador global del header. El menu contextual de cada activo puede abrir `Itinerarios` dentro del mismo panel lateral, generar el recorrido del vehiculo, mostrar el resumen diario de solo ese activo o agregarlo al resumen diario actual. La accion `Agregar a resumen diario` se expone solo despues de iniciar un resumen diario, usando el estado `hasActiveDailySummary`, para evitar que aparezca antes de existir un resumen al cual sumar activos. Tambien puede navegar a `Mantenciones` con `assetId`, `patente` y `open=maintenance-detail` para abrir las mantenciones del vehiculo seleccionado. En la seccion `Geocercas`, coordina importacion/exportacion KML, KMZ, GeoJSON, CSV y XML, creacion/renombrado/eliminacion de grupos, auditoria y refresco del mapa. Los grupos se gestionan solo en el panel lateral; el editor del mapa solo los selecciona desde dropdown o deja la geocerca sin grupo.
- `AuditView.vue`: vista de auditoria.
- `CompanyManagementView.vue`: vista de administracion de empresas. Usa topbar
  oscuro, cabecera de gestion, busqueda/filtros/KPIs y tarjetas de empresas en
  dos columnas. El catalogo debe priorizar acceso rapido a cada empresa y sus
  acciones principales.
- `LoginView.vue`: vista de inicio de sesion.
- `MaintenanceView.vue`: vista visual de mantenciones. Conecta router, servicio de acceso, componentes visuales y `useMaintenanceModule`; las pestanas grandes, paneles reutilizables y modal operativo viven en `frontend/src/components/maintenance`. Acepta `assetId`, `activoId`, `asset`, `patente`, `plate` o `ppu` en query para seleccionar un vehiculo; con `open=maintenance-detail` abre directamente el modal de mantenciones del vehiculo.
- `NoAccessView.vue`: vista de acceso denegado.
- `ReportsView.vue`: vista de reportes. Usa formato de biblioteca con cabecera,
  busqueda, acciones de reglas/programados/nuevo, tabs `Todos/Creados/Base`,
  filtros de categoria y orden, vista por cards como modo principal, lista
  secundaria y paginacion sin cambiar los modales ni la logica de plantillas.
  Las cards deben mantenerse compactas y mostrar solo identidad, descripcion,
  evento, estado y acciones principales para editar o ejecutar. Al ejecutar
  desde esta vista se debe reutilizar `ReportExecutionModal`, con activos
  filtrados por permisos y por la empresa actual cuando exista `empresaId` en la
  ruta, para mantener el mismo comportamiento de ejecucion que Fleet sin tocar
  `FleetReportsPanel.vue`. Para aprovechar el espacio libre, aumentar
  la cantidad visible por pagina antes que agregar paneles secundarios o inflar
  las tarjetas, pero manteniendo la paginacion visible. La grilla debe usar altura natural y `content-start`; no forzar
  `h-full` ni filas fijas en escritorio grande porque agranda las cards
  innecesariamente. Si no caben todas, es preferible scroll normal antes que
  cortar eventos, estado o accion.
- `UserManagementView.vue`: vista de administracion de usuarios. Orquesta un panel administrativo: topbar con buscador, KPIs filtrables sin iconos, filtros/directorio a la izquierda y detalle con tabs a la derecha.

## Regla de mantenimiento

Las vistas deben orquestar componentes y composables. Si una vista crece demasiado, extraer secciones visuales a `components` y estado a `composables`.

Los modales pesados de vistas principales deben cargarse con `defineAsyncComponent`
y precargarse con `preloadWhenIdle` despues del primer render. Mantener `v-if`
en el padre cuando el modal esta cerrado para no ejecutar formularios, watchers
o calculos de preview hasta que realmente se usen.

`LoginView.vue` usa `frontend/public/login-dashboard-hero.jpg` como hero visual activo. Es una version optimizada del PNG original para bajar la carga inicial del login. La imagen se mantiene completa con `background-size: contain` y alineada a la derecha para evitar espacio negro en el borde derecho; el sobrante queda bajo la zona del formulario. El logo del login se carga desde `frontend/public/logo-sinergy.html` mediante un `iframe` dentro de `.login-logo-frame`, para usar la animacion HTML local sin duplicarla dentro de la vista; el iframe se desplaza levemente dentro del marco para compensar el margen transparente interno del SVG y alinear el borde visual del logo con el formulario. Si se cambia esa imagen o animacion, el archivo referenciado en `LoginView.vue` debe existir realmente en `public` y se debe actualizar el query de cache en `loginHeroImagePath` cuando corresponda.

Los iconos del formulario de login se fuerzan con `z-index`, color corporativo y `:deep(svg)` para mantener buen contraste dentro de los inputs oscuros, incluso cuando `SvgIcon.vue` renderiza el SVG como componente hijo. Los iconos de usuario y contrasena comparten el mismo contenedor; el SVG de usuario recibe una compensacion leve de tamano y brillo porque su arte interno pesa menos visualmente que el candado.

Cuando se actualice una vista o documentacion relacionada con el funcionamiento general del frontend, revisar si `a.html` y `frontend/docs` tambien deben reflejar el cambio.

En `a.html`, la seccion de cuellos de botella debe mostrar solo deudas vigentes; los puntos ya mitigados deben moverse a notas de mantenimiento o eliminarse de esa lista.

`AuditView.vue` usa una base gris/azul suave para reducir fatiga visual en tablas largas. La composicion superior sigue el orden filtros, KPI y tabla, apoyandose en el header global para el contexto principal de la vista. Sus controles y KPI deben mantenerse compactos para no empujar la tabla hacia abajo. Sus componentes refuerzan la identidad visual con azul corporativo en encabezados y naranjo en acciones o seleccion; el detalle de la paleta esta en `frontend/src/components/audit/README.md`. La vista pagina la tabla en bloques de 150 registros sin afectar filtros, KPI ni exportacion CSV. Tambien filtra por accion, por rango de fechas `Desde`/`Hasta` de forma inclusiva por dia completo y permite buscar fechas desde la barra general con formatos comunes.

`MaintenanceView.vue` es un prototipo funcional local. No crea `localStorage` nuevo ni llama backend: las acciones de nueva mantencion, nuevo tipo de mantencion, nueva OT, editar, reprogramar, asignar, cancelar, cerrar, registrar costo y exportar viven en refs temporales dentro de `frontend/src/composables/maintenance/useMaintenanceModule.js` y se pierden al recargar. La pantalla toma las patentes desde `assets` filtrados por `route.params.empresaId`, por lo que `/app/:empresaId/mantenciones` muestra solo vehiculos de la empresa abierta; los fallback de demo quedan reservados para la vista general sin empresa. Las mantenciones, agenda, OT, historial y costos siguen siendo datos de demostracion coordinados por el composable, con configuracion estatica y helpers puros en `frontend/src/utils/maintenance`. La vista quedo modularizada visualmente: resumen, ordenes, calendario, historial, costos, paneles reutilizables y modal operativo son componentes presentacionales, mientras la logica queda centralizada para no cambiar comportamiento durante el prototipo. La creacion de mantenciones conserva la esencia del modulo antiguo: primero se elige un tipo existente desde un dropdown y ese valor pasa a ser tambien el nombre de la mantencion; luego se elige el vehiculo y se configura intervalo/alerta. Ese formulario no muestra acciones para crear tipos ni nombre editable. La creacion de tipos vive en un modal separado, donde se define nombre y criterio base: odometro, horometro o tiempo. Al seleccionar el tipo en una mantencion, el criterio de lectura se marca automaticamente segun lo definido al crear ese tipo. El formulario evita duplicados visibles por vehiculo, configura intervalo/alerta y calcula estado por odometro, horometro, fecha/hora o valor manual. Cada plan manual guarda `companyId` y `plate`, ademas de `vehicleId`, para mantener la relacion empresa + patente como en el flujo anterior. Crear una mantencion no genera una OT automaticamente; solo deja el plan disponible para seguimiento.

La prioridad funcional del modulo es `Ordenes de trabajo`: desde ahi crecen la creacion, asignacion, reprogramacion, cancelacion, cierre, costos, facturas y seguimiento de mantenciones. La OT no es lo mismo que una mantencion: la mantencion es el plan o regla de control, y la OT es la ejecucion concreta del trabajo. La OT nace como accion explicita desde el detalle de mantenciones o desde `Ordenes de trabajo`; si corresponde, queda asociada a una `maintenancePlanId` para conservar plan, lectura, intervalo y estado de origen. `Historial` y `Costos y facturas` quedan ligados al vehiculo seleccionado para mostrar trazabilidad, taller/responsable, documentos y montos. `Calendario OT` se mantiene como apoyo visual secundario, no como flujo principal.

El flujo funcional vigente para el prototipo es: activo con GPS, seleccion de template, lecturas de odometro/horometro/fecha o valor manual, configuracion de intervalo y alerta, calculo de estado de mantencion, decision operativa de crear una OT, programacion/ejecucion, cierre con costo/factura/repuestos/observaciones, historial por vehiculo y proximo ciclo. Todo lo relativo a automatizacion real de API, backend, n8n, correo o WhatsApp queda fuera de esta vista por ahora; si se muestra algo relacionado debe ser informativo o pendiente, no integracion real.

La pestaña `Resumen` debe parecerse al panel principal de mantenciones de referencia: KPI por estado arriba, filtros compactos debajo y la tabla de vehiculos como elemento central. Debe intentar entrar completa en la vista, por eso usa una primera pagina visual de 5 vehiculos y deja la paginacion como indicacion inferior en vez de alargar el contenido. Los KPI usan `SvgIcon.vue` para mantener consistencia con la iconografia del proyecto (`ok`, `mantenciones`, `vencida`, `configuracion` y `llave` para `En taller`) y se renderizan dentro de `.maintenance-summary-icon`, que fuerza tamaño y centrado uniforme aunque el SVG traiga clases internas; si un icono se ve desplazado, se corrige en el vector base antes que con margenes puntuales. La tabla reutiliza esos mismos iconos por estado mediante `getSummaryMetricIcon`, y tambien mantiene centrado uniforme en la columna de estado, contadores de mantenciones activas y botones de accion para evitar que los iconos queden pegados a un borde. La accion de ver abre un modal de mantenciones del vehiculo, mostrando ultimo registro, lectura actual, umbral, faltante, alerta y acceso directo para crear OT desde ese plan. No debe mezclar paneles auxiliares debajo de la tabla mientras se este validando la propuesta visual. En el resumen, el horometro se muestra solo si existen vehiculos con ese dato; cuando un vehiculo no lo trae, se representa con `-` para evitar obligar una columna que no aplica a toda la flota. El boton `Exportar` queda como accion secundaria visual hasta definir si realmente aporta al flujo.

El modal de mantenciones del vehiculo usa una grilla de fichas compactas similares al modulo anterior, porque un mismo vehiculo puede tener varias mantenciones configuradas. La cabecera identifica el vehiculo y permite tanto agregar una mantencion al activo como crear un nuevo tipo de mantencion desde el mismo contexto del ojo. Cada card representa un plan independiente con criterio de lectura, intervalo, ultimo registro, umbral, lectura actual, faltante, alerta, contacto/origen y acciones directas para crear OT, editar o eliminar. La grilla incluye una ficha punteada para agregar otra mantencion. Las mantenciones manuales se editan y eliminan desde la misma ficha; si el usuario edita una mantencion base visual, se guarda como configuracion manual del vehiculo. La base visual no se elimina directamente porque se deriva de la fila del vehiculo. Evitar paneles oscuros, timelines o barras de avance en esta vista; el objetivo es lectura rapida por mantencion y buena escalabilidad visual cuando existan varias.

La pestaña `Ordenes de trabajo` tiene layout propio para acercarse a la referencia de OT: encabezado compacto, KPI filtrables por estado, filtros especificos de orden (`orderSearchTerm`, `selectedOrderStatus`, `selectedOrderPriority`, `selectedOrderWorkshop`), tabla principal con maximo visual de 10 filas y panel lateral de detalle. No usa los filtros genericos de mantencion para evitar mezclar estados de vehiculo con estados de OT. Al seleccionar una orden se sincroniza `selectedVehicleId` con el vehiculo de esa OT, de modo que el detalle, historial y costos sigan apuntando al activo correcto. El boton de ojo de una OT no reemplaza la seleccion de fila: abre el modal de mantenciones del vehiculo asociado para revisar sus planes y crear una OT desde una mantencion si corresponde. Los iconos de estado de OT reutilizan `SvgIcon.vue` mediante `getOrderStatusIcon`. El formulario de OT permite elegir una mantencion origen; al seleccionarla autocompleta trabajo, tipo, lectura e intervalo, y el detalle muestra si la orden es `Mantencion` o `Manual`.

`UserManagementView.vue` bloquea el filtro de empresa cuando entra desde `/app/:empresaId/usuarios`, para mantener el contexto del panel de Fleet. El layout se divide en topbar/KPIs, filtros, directorio y detalle con tabs. El detalle visual del modulo esta documentado en `frontend/src/components/users/README.md` y la logica de filtros en `frontend/src/composables/users/README.md`.
